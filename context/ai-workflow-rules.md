# AI Workflow Rules

## Approach

Plan-driven. `CLAUDE.md` holds the owner's rules; `context/pending-work.md` holds what is left to build; `reference/PROJECT-GUIDE.md` explains the design. Read `progress-tracker.md` first,
build in the plan's order, and change the plan only for a stated reason (a better or simpler option found by research).
Record every deviation in the tracker.

## Scoping rules

- One feature unit at a time; small, verifiable increments with a test each.
- Do not mix unrelated boundaries in one step (conversation core, mock bank, UI, evals).
- If a change cannot be verified quickly end to end, split it.

## Never without being asked (from CLAUDE.md)

- Commit or push to git.
- Restart, stop or replace the owner's running demo (`python app.py` on :8000, `bun run dev` on :3000). The UI hot-reloads;
  the brain needs a restart, and replies must say so.
- Print, log or echo the Groq key. Modify the dummy workbook.
- Run the full benchmark casually (Groq free tier: 1,000 requests per day per model).

## Missing or ambiguous requirements

- Do not invent product behaviour. Add an open question to `progress-tracker.md` and pick the safest default meanwhile.

## Protected files

- `Sample Questions/` (the workbook and source KB documents) are never edited. Corrected copies go under `brain/seed/`.
- `ui/components/ui/*` is generated by the shadcn CLI.

## Keeping docs in sync

After each meaningful change update: `progress-tracker.md` (what, numbers, live vs needs restart, next step). If architecture,
scope or rules changed, also `reference/PROJECT-GUIDE.md`, the relevant README, `architecture.md` or `CLAUDE.md`, in the same piece of work.

## Before moving to the next unit

1. It works end to end within its scope; its tests pass (`uv run pytest -m "not live"`).
2. No invariant in `architecture.md` was violated.
3. Accuracy and latency are no worse (measured, or stated as not measured).
4. `progress-tracker.md` reflects it. `bun run build` passes if the UI changed.
